# DeveloperTools

This repo
(`LWHSTechnicalArts/DeveloperTools` on GitHub) makes every student machine match
the p5.js web editor's **light** color scheme in Visual Studio Code and
the zsh prompt.

The setup must install with a bash script and a few shared files: no menu
navigation and no point-and-click steps.

## Repo contents

The repo is the single source of truth. Since 2026-10-17, the live
locations on Jeffrey's machine are **symlinks** into this repo (three settings files; the two local extensions were also linked until 2026-10-19, see below), so edits here
take effect live, and changes made through Visual Studio Code's Settings screen
land in `vscode/settings.json`. The originals are backed up in
`~/DeveloperTools-backups/2026-10-17/`. A program that rewrites one of these files
can replace its link with a regular file; check with `ls -la` (look for `->`).

The repo has five folders: `scripts/` (the four setup scripts plus `configure-copilot.sh`, `refresh-copilot.sh` and `update-worksheets.sh`), `zsh/` (`.zshrc` and the Powerlevel10k config), `vscode/` (`settings.json`, `extensions.txt`, and the theme extension), `copilot/` (Copilot's class instructions, `worksheets.txt`, and `worksheets/`), and `docs/` (four flowchart images: `setup-flow.png`, the order the setup scripts run in; `file-map.png`, where each repo file goes on a student's Mac and how `copilot/` changes reach students; and `worksheet-sync.png`, the hourly worksheet workflow from a Google Doc edit or a `worksheets.txt` change through `update-worksheets.sh`, the bot commit, and `refresh-copilot.sh` on students' Macs; and `copilot-refresh.png`, how the launch agent and the Refresh Copilot button run `refresh-copilot.sh`'s three checks how the button then restarts the local agent host and opens a new chat, and how each VS Code launch opens a new chat; drawn as SVG by a Python script and rendered with `rsvg-convert -w 2200`, neither kept in the repo). The hidden `.github/workflows/` folder holds `update-worksheets.yml`. `configure.sh` finds the repo root as the parent of `scripts/`. The scripts set up a Mac. Their comments teach bash to students, so keep
them accurate and in that teaching style when editing. They must run on macOS's
built-in bash 3.2: no associative arrays, `mapfile` or `${variable,,}`. Every
step skips work that is already done, so each script is safe to rerun.

- `bootstrap.sh` is what students run first, with the one-line command in `README.md`: `caffeinate -dis /bin/bash -c "$(curl -fsSL https://raw.githubusercontent.com/LWHSTechnicalArts/DeveloperTools/main/scripts/bootstrap.sh)"` (`caffeinate` keeps the Mac awake for the whole run: `-d` display, `-i` idle sleep, `-s` system sleep on AC power, per `man caffeinate`). It uses `set -Eeuo pipefail` plus a `trap ... ERR` that prints the failing line number and tells the student to paste the command again, so failures are never silent. Running it through `bash -c` (not `curl | bash`) keeps the terminal as standard input, so `sudo` and `read` work. It installs Apple's Command Line Tools if `xcode-select -p` fails, using Homebrew's headless method (a placeholder file in `/tmp`, then `softwareupdate -i` with the newest "Command Line Tools" label) and falling back to `xcode-select --install` plus a Return-to-continue prompt; then, if `xcode-select -p` is inside an Xcode app and `xcodebuild -license check` fails (on a test Mac on 2026-10-19, Apple's `git` showed its own license prompt and then quit without cloning, which ended the script silently), it runs `sudo xcodebuild -license` so the student can type `agree` and continue, and exits with a message if `git --version < /dev/null` still fails (README setup step 4 tells students how to accept); it clones the repo into `~/DeveloperTools`, or, if it is already there, first runs `git stash push -m "settings.json before update" -- vscode/settings.json` (added 2026-10-24: the linked `settings.json` always has local changes on student Macs, at least from the theme's one-time rewrite, and those made `git pull` refuse every upstream `settings.json` change; the stash sets them aside and restores the committed file, works with no Git name or email configured, and saves nothing when the file is clean) and then runs `git pull --ff-only` (continuing on failure), and refuses if `~/DeveloperTools` exists but is not a git repository; then it `exec`s `scripts/setup.sh`. Students get `bootstrap.sh` from `main` on GitHub, so changes reach them only after a push.
- `setup.sh` runs the install and configure steps (`bash scripts/setup.sh` from the repo folder). It runs `install.sh`, then runs `configure-copilot.sh` and `configure.sh` only if `install.sh` exited with status 0 (`configure-copilot.sh` first, so an extension failure in `configure.sh` cannot block it); otherwise it prints an error and exits 1.
- `install.sh` installs, in order: Homebrew (`sudo -v` caches the administrator password, then the official installer runs with `NONINTERACTIVE=1`, which makes it use `sudo -n`); the `brew shellenv` line appended to `~/.zprofile`; Visual Studio Code with `brew install --cask` (skipped when the app is already in `/Applications`, since `brew` refuses to overwrite an app it did not install); the Homebrew formulae `zsh-autosuggestions` and `zsh-syntax-highlighting`; oh-my-zsh (`KEEP_ZSHRC=yes`, `--unattended`); `git clone --depth=1` of Powerlevel10k into `~/.oh-my-zsh/custom/themes/powerlevel10k`; and the four MesloLGS NF `.ttf` files from `romkatv/powerlevel10k-media` into `~/Library/Fonts`. Last, it installs the Homebrew cask `font-inconsolata` (Inconsolata, SIL Open Font License) for the editor.
- `configure.sh` recreates the three settings symlinks (`.zshrc`, `.p10k.zsh`, VS Code `settings.json`), moving anything in the way into `~/DeveloperTools-backups/<date_time>/` and creating missing parent folders. It then installs each extension in `vscode/extensions.txt` (one `publisher.name` per line; `#` comments and blank lines skipped) with `code --install-extension`, using `code` from the command path or from inside `/Applications/Visual Studio Code.app`. The list holds `samplavigne.p5-vscode`, `ritwickdey.LiveServer` and `usernamehw.errorlens`; p5.vscode's extension pack already includes Live Server, and Live Server is not built into Visual Studio Code. GitHub Copilot is built in (`GitHub.copilot-chat`), so it is not in the list. It then packages each folder in `local_extension_folders` (`vscode/p5js-editor-light`, `vscode/p5-live-sketch`, `vscode/refresh-copilot`) into a `.vsix` with `zip` (an `extension/` folder plus `extension.vsixmanifest` and `[Content_Types].xml`, with publisher, name, version, display name and engine read from `package.json` by `plutil -extract FIELD raw`) and installs it with `code --install-extension FILE --force`, after moving any old symlink at `~/.vscode/extensions/FOLDER` into the backup folder. On 2026-10-19 a test Mac showed that VS Code did not load folders symlinked into `~/.vscode/extensions` (theme and Live Sketch both silently missing), though Jeffrey's own machine had registered them; `.vsix` installs registered both in an isolated `--extensions-dir` test. Installed copies are not live: after editing either folder, rerun `configure.sh`.
  On 2026-10-21 on Jeffrey's Mac, the first run after the switch from symlinks moved both old extension symlinks to the backup folder, installed the theme, then failed on Live Sketch with `Please restart VS Code before reinstalling p5.js Live Sketch.` ; `set -e` stopped the script there. VS Code was not the cause: the error persisted with VS Code closed. VS Code's code (`cliProcessMain.js`) shows that installing a `.vsix` whose name and version match a registered extension first deletes the registered folder, and reports any delete failure with that message; Live Sketch 0.0.1 was still registered at the moved symlink's path. `code --uninstall-extension local.p5-live-sketch` cleared it and the install succeeded. `configure.sh` now runs that uninstall right after moving an old symlink (that branch is untested).
- `vscode/refresh-copilot/` (installed as `local.refresh-copilot`, added 2026-10-21 at Jeffrey's request) adds a "$(sync) Refresh Copilot" status bar button (left side, activates on `onStartupFinished`) and the command `refreshCopilot.refresh` ("Refresh Copilot: Update Class Instructions"). It finds the repo by resolving the `~/.copilot/copilot-instructions.md` link, runs `scripts/refresh-copilot.sh` with `/bin/bash`, and shows an information, warning ("Skipped:") or error message. Since version 0.0.2 (2026-10-25), when the folder was updated or was already current, it runs "Restart Local Agent Host" (`workbench.action.chat.restartLocalAgentHost`), then, since version 0.0.3 (Jeffrey's request, so students never keep typing into a chat with the old instructions), opens a fresh chat with `workbench.action.chat.newChat` followed by `workbench.action.chat.open` (the same pair VS Code's own code uses), falling back to "Click + in the chat to start a new chat" if either fails. Since version 0.0.4 (2026-10-25) it also runs that new-chat pair, silently, each time VS Code finishes starting (`onStartupFinished`), because on the 2019 MacBook Pro after a bootstrap rerun the chat already open at startup had no class instructions while a chat started with + did (VS Code's `chat.restoreLastPanelSession` defaults to `false`, so that startup chat was not a restored one). Jeffrey confirmed on 2026-10-25 that this works as desired on the 2019 MacBook Pro; if that command does not exist it says to quit and reopen VS Code. Reason: on the 2019 MacBook Pro the instructions file on disk was current but Copilot kept answering from the previous version through "Reload Window" (which 0.0.1 offered); Jeffrey ran "Restart Local Agent Host" by hand and that cleared it. It restarts even when the script reports nothing new, because the launch agent may already have updated the folder in the background. All five result paths passed against a stubbed `vscode` module and throwaway repos; the button itself has not been seen in VS Code yet. The `--force` reinstall of all three local extensions succeeded with VS Code open.
- `configure-copilot.sh` is kept apart from `configure.sh` (Jeffrey's request, 2026-10-21) because the Copilot instructions change often and the extensions rarely. It links `~/.copilot/copilot-instructions.md` to `copilot/copilot-instructions.md` (only that file, because `~/.copilot` also holds Copilot's own data), then writes the launch agent `~/Library/LaunchAgents/org.lwhs.developertools.refresh-copilot.plist` (via a here document, with the repo path filled in) and loads it with `launchctl bootout` then `launchctl bootstrap gui/$(id -u)`, skipping when the file is unchanged and `launchctl print` shows it loaded. The agent runs `scripts/refresh-copilot.sh` at minutes 0, 15, 30 and 45 (`StartCalendarInterval`, which runs a missed time on wake, per `man launchd.plist`) and logs to `~/Library/Logs/DeveloperTools-refresh-copilot.log`. Loaded on Jeffrey's Mac on 2026-10-21; a `launchctl kickstart` run exited 0 and fetched from GitHub. An actual folder update through `launchd` is untested.
- `refresh-copilot.sh` makes only `copilot/` match GitHub: `git fetch -q origin`, then `git checkout -q --no-overlay origin/main -- copilot` (`--no-overlay` deletes files removed upstream). A full `git pull --ff-only` would stop whenever a student's `vscode/settings.json` had local edits from the Settings screen. It fetches first, then skips when `HEAD` has commits not on `origin/main`, or when `copilot/` matches none of the last 100 versions of `copilot/` on `origin/main` (`git rev-list -n 100 origin/main -- copilot`), so Jeffrey's own unpushed, uncommitted or staged work is never overwritten. Until 2026-10-25 the second check compared only `HEAD` and the pre-fetch `origin/main`, which can get stuck for good ("Skipped: the copilot folder has local changes." on every run), the likely but unconfirmed cause of a failed button refresh on a 2019 MacBook Pro on 2026-10-25: after a refresh, the setup command's `git pull --ff-only` fetched a newer version but refused to merge over the staged refreshed files, so they matched neither. Reproduced and fixed in throwaway repos; eight student and teacher scenarios passed. Measured 2026-10-21: one fetch from GitHub took about 0.27 s of wall time and 0.05 s of processor time. The refreshed files show as staged changes in `git status`; `bootstrap.sh`'s later `git pull --ff-only` still succeeds (tested in throwaway repos).
- `update-worksheets.sh` is never run by students. Since 2026-10-21 the GitHub Actions workflow `.github/workflows/update-worksheets.yml` runs it at minute 17 of every hour (and on demand from the Actions tab) on `macos-latest`, because the script uses macOS's `sed -i ''`; if `git status --porcelain -- copilot` shows changes, it commits them to `main` as `github-actions[bot]` with the message "updated worksheets from google docs" and pushes with the run's token (`permissions: contents: write`). Bot commits skip the by-hand review, and they land on GitHub's `main`, so pull before pushing local commits. GitHub disables scheduled workflows in a public repository after 60 days with no repository activity. Jeffrey can still run the script by hand. Since 2026-10-21 (Jeffrey's request), `copilot/worksheets.txt` holds one Google Doc share address per line, in class order, so a person only pastes an address; anything after the first space is the title the script writes back. The script downloads each Doc from `https://docs.google.com/document/d/ID/export?format=md` into a `mktemp -d` folder (so a failed download leaves the old worksheets), reads the Doc's title from the `filename*=UTF-8''...` part of the `content-disposition` header (`curl -D`), names the file `NN-title-slug.md` by list position, deletes the embedded base64 pictures with `sed` (they made the nine worksheets 5.4 MB; without them, 58 KB), then replaces `copilot/worksheets/` (dropping worksheets removed from the list). It rewrites `worksheets.txt` as `ADDRESS  Title` lines (comments kept) and replaces the numbered list in `copilot-instructions.md` between `<!-- worksheet list: written by scripts/update-worksheets.sh -->` and `<!-- end of worksheet list -->`, exiting 1 if either marker is missing. The bot therefore commits to `copilot-instructions.md` too, so pull before editing it. Titles come from the Docs themselves (for example "Variables and Conditional Statements Fall 2026"). Tested 2026-10-21: a second run changed nothing, and in a scratch copy a removed line and a pasted bare address were renumbered and listed correctly. Review with `git diff`, then commit.

Facts about these files that matter for distributing them to students:

- `.zshrc` has no machine-specific paths. It uses `$HOME/.oh-my-zsh`. When `HOMEBREW_PREFIX` is unset (a shell that skipped `~/.zprofile`, such as one started with `exec zsh`), it runs `brew shellenv` from the first of `/opt/homebrew/bin/brew` and `/usr/local/bin/brew` that exists, then loads both zsh plugins from `$HOMEBREW_PREFIX/share/...`, skipping them if no Homebrew is found. Before 2026-10-25 it fell back to `/opt/homebrew` only: on the 2019 Intel MacBook (macOS 15.7.7, Homebrew in `/usr/local`), a non-login `zsh -i` printed two `no such file or directory: /opt/homebrew/share/...` errors and had no plugins and no `brew`. Tested 2026-10-25 with a clean environment: login and non-login shells on Jeffrey's Mac (`/opt/homebrew`) and on the 2019 Mac (`/usr/local`, via a temporary `ZDOTDIR` copy) all loaded both plugins and found `brew`. Its last line sources `~/.zshrc.local` if that file exists.
- `.zshrc` adds `/Applications/Visual Studio Code.app/Contents/Resources/app/bin` to `PATH` when `code` is not already a command (2026-10-19). The Homebrew cask links `code` into Homebrew's bin, but `install.sh` skips the cask when VS Code is already in `/Applications`, and on a test Mac with a hand-installed VS Code, `code .` failed with the `command_not_found_handler` message. The line follows VS Code's macOS setup guide (https://code.visualstudio.com/docs/setup/mac).
- Intel Macs: Homebrew 7.0.0 moved Intel `x86_64` to Tier 3 in September 2026 (no new bottles; updated formulae may build from source) and stops running on Intel Macs on 2027-09-01 (https://brew.sh/2026/09/13/homebrew-7.0.0/). The setup's two formulae have architecture-independent `all` bottles, and its casks (Visual Studio Code, `font-inconsolata`) are app downloads, so they are unaffected until that removal. On the 2019 Mac everything else installed and ran: Visual Studio Code 1.143.1 (x64), all local extensions, both fonts, the links, and the Copilot refresh agent.
- Machine-specific shell settings go in `~/.zshrc.local`, which lives outside the repo. Jeffrey's holds only the conda block. The TeX path comes from `/etc/paths.d/TeX` and `$HOME/.local/bin` from `~/.zprofile`. Put new personal settings there, not in `.zshrc`.
- `vscode/settings.json` sets `editor.fontFamily` to `Inconsolata, Menlo, monospace` so the editor looks different from the terminal (`terminal.integrated.fontFamily` is `MesloLGS NF`), because beginners confuse the two. Consolas was the first model, but it is a proprietary Microsoft font that cannot be installed by script; Inconsolata's designer cites Consolas as an inspiration (https://levien.com/type/myfonts/inconsolata.html). Roboto Mono was tried more than once on 2026-10-17; Jeffrey's current choice is Inconsolata. `editor.fontSize` and `terminal.integrated.fontSize` are both 18 (pixels), matching the p5.js web editor's default `fontSize: 18` in `client/modules/IDE/reducers/preferences.ts`.
- Microsoft's Live Preview extension (`ms-vscode.live-server` 0.4.20) was tried on 2026-10-18 as a more integrated replacement for Live Server. Its preview did not auto-refresh on editor changes in a p5.js project, with either `livePreview.useIntegratedBrowser` true (the default) or false, so the tour stays on Live Server. Live Server's reload works in any browser because it injects a script into served pages that reloads them over a WebSocket (`node_modules/live-server/injected.html`). Jeffrey confirmed on 2026-10-18 that the Live Server page auto-refreshes inside VS Code's integrated browser. Since PR #1 (merged 2026-10-19), the p5.js Live Sketch extension does this automatically and `settings.json` sets `liveServer.settings.NoBrowser: true`, so Go Live no longer opens an external browser. README tour step 18 says the sketch appears beside the code on its own, step 21 watches it update, and step 22 (optional) copies the address into an external browser. Known gap: "Developer: Reload Window" opens a second integrated browser tab instead of reusing the restored one; set aside because students do not reload windows. On 2026-10-19 a startup log showed why reopening a project flashed a "failed to load" page: VS Code restores the project's previous integrated browser tab (`127.0.0.1:5500`) and loads it about 6 seconds before the extension activates, while Live Server is not yet running; the extension then closed it within 0.25 s and showed the working sketch within 0.6 s. Because no extension can run before that restore, `settings.json` sets `workbench.editor.restoreEditors: false`, so VS Code reopens no editor tabs on startup in any window, and the extension opens `sketch.js` and the sketch itself.
- p5.vscode 1.2.16 (last updated 2024-08-09) ships `p5types/tsconfig.json` with a `files` list naming `test/index.ts` and `test/unaugmented.ts`, which the extension does not include, and `"baseUrl": "../"`, which TypeScript 6 (bundled with VS Code 1.142) marks deprecated. Any project made with Create p5.js Project gets a `jsconfig.json` that includes `p5types/global.d.ts`, so VS Code loads that tsconfig and shows 3 errors in the Problems panel. `configure.sh` therefore overwrites the file (with a here document) with a copy that drops `baseUrl` and lists only `index.d.ts`, skipping it when `baseUrl` is already gone. Checked with VS Code's TypeScript 6.0.3: original 3 diagnostics, patched 0, and no type errors. Reinstalling the extension restores the original, so rerun `configure.sh`.
- To make mistakes easier to see and fix (2026-10-18): `editor.guides.bracketPairs: true` in `settings.json`; the Error Lens extension in `extensions.txt` (Code Spell Checker was added and then removed the same day); and a `command_not_found_handler` function in `zsh/.zshrc` that prints `"NAME" is not a command. Check the spelling, or press the Up arrow to fix it.` to standard error and returns 127, so the prompt still shows the failure mark.
- To make the terminal safer and more legible (2026-10-18): `zsh/.zshrc` defines an `rm` function that prints `(Type y and press Return to delete, or n and Return to keep.)` to standard error and then runs `command rm -i` on each file. Since 2026-10-25 (Jeffrey's request: students must not delete without confirming), it strips every `f` from the options, because `-f` overrides `-i`; for a folder named with `-r` or `-R` (not a symbolic link) it instead asks once, `Do you want to delete the folder "NAME" and all of its contents? (y/n)` (Jeffrey's wording), and on `y` runs `command rm` with the remaining options and no `-i`. Tested with deletion replaced by a printout (11 cases). `command rm` and `/bin/rm` still bypass the function (macOS `rm` cannot change its own "remove FILE?" wording, per `man rm`; a later `-f` overrides `-i`) and `alias ls='ls -FG'` (trailing `/` on folders; `-G` keeps the color oh-my-zsh's `ls -G` alias gave); `settings.json` sets `editor.mouseWheelZoom: true` (Command-scroll zooms the editor) and `terminal.integrated.cursorStyle: "line"`.
- To behave like the p5.js web editor, whose defaults include `autosave: true` and `linewrap: true` (`client/modules/IDE/reducers/preferences.ts`), `vscode/settings.json` sets `files.autoSave: "afterDelay"` and `editor.wordWrap: "on"` (2026-10-18). Autosave also means Live Server shows the latest code without a manual save. Line numbers and auto-closing brackets and quotes are already Visual Studio Code defaults.
- To reduce clutter for beginners (2026-10-18), `vscode/settings.json` turns off sticky scroll (`editor.stickyScroll.enabled: false`), and opens to an empty window (`workbench.startupEditor: "none"`). Breadcrumbs, the file path above the editor, stay on by Jeffrey's choice, and so does the minimap (`editor.minimap.enabled: true`), which he turned back on.
- `vscode/settings.json` sets `security.workspace.trust.enabled: false` (Jeffrey's choice, 2026-10-19). On the test Mac the Workspace Trust prompt opened new p5.js project folders in Restricted Mode, which disables extensions that have not opted into it, so the theme's one-time apply and p5.js Live Sketch did not run. Trade-off: any folder a student opens, including a downloaded one, can run its tasks and its extensions' code without a warning; VS Code's docs call disabling trust "not recommended" (https://code.visualstudio.com/docs/editing/workspaces/workspace-trust). The alternative considered was trusting the parent Documents folder once from the prompt.
- `vscode/settings.json` sets `github.copilot.chat.agentDebugLog.fileLogging.enabled: true` (Jeffrey's request, 2026-10-25; the Copilot extension's default is `false`, per `extensions/copilot/package.json` in VS Code 1.142.0), so "Developer: Open Agent Debug Logs" works when diagnosing why Copilot Chat ignored the class instructions on a student Mac. Its description says it writes chat debug events to JSONL files and "Requires window reload to take effect."

They are user settings, so a student can turn them back on; only the Claude and Codex settings also have enterprise policies (`Claude3PIntegration`, `Codex3PIntegration`). It still has entries for extensions students do not get: Vim cursor style and two Claude Code options, plus GitHub Copilot options.

## Decisions and reasons

- iTerm2 was removed from the student setup on 2026-10-17 to reduce complexity: students use Visual Studio Code's built-in terminal, whose font, size and colors all come from `settings.json` and the theme with no manual steps. iTerm2 needed a by-hand font change. The guarded iTerm2 `SetColors` block stays in `.zshrc` because it does nothing in other terminals. The iTerm2 notes below are kept as history.
- The prompt uses no green, because light green is unreadable on white. Clean version-control state and success status are blue; untracked files are brown.
- Exception, by Jeffrey's choice on 2026-10-17: zsh-syntax-highlighting colors invalid commands a pale yellow-green, bold `#afc641` (`#96b403` mixed 25% toward the page color `#fbfbfb`), set as `ZSH_HIGHLIGHT_STYLES[unknown-token]` in `zsh/p5js-editor-light.p10k.zsh`. It is deliberately outside the p5.js palette so mistakes look clearly wrong next to the magenta accent. It contrasts about 1.9:1 on `#fbfbfb`, the background of iTerm2 and of Visual Studio Code's terminal. Valid commands stay blue `#0b7ca9`, reserved words brown `#7a5a3a`.
- The prompt has two lines. The top line has directory and version-control segments on the left and status, command duration and background jobs on the right (the clock was removed on 2026-10-18 to reduce clutter; its `POWERLEVEL9K_TIME_*` color settings remain, unused). The second line has the prompt character.
- Hexadecimal prompt colors need a terminal with 24-bit color.
- `ZSH_HIGHLIGHT_STYLES` only takes effect when the zsh-syntax-highlighting plugin is installed.
- Colors printed by programs such as Homebrew come from the terminal palette, not the prompt. The `.zshrc` block sets the whole iTerm2 palette per session with `OSC 1337 ; SetColors=key=value`, guarded by `TERM_PROGRAM == iTerm.app`, after the line that sources `~/.p10k.zsh`. Source: https://iterm2.com/documentation-escape-codes.html
- Set the palette in one block. Jeffrey rejected palette lines added one slot at a time. Keep color changes inside the named config files, not in ad hoc palette lines.
- Visual Studio Code's terminal background is `#fbfbfb` (`terminal.background` in the theme), matching the editor and iTerm2, by Jeffrey's request on 2026-10-17; it was the console grey `#f0f0f0`. The surrounding panel (`panel.background`) stays `#f0f0f0`. The prompt's version-control and status segments keep `#f0f0f0` backgrounds, so they now show as light grey blocks, and the prompt character's `#fbfbfb` background blends in.
- `terminal.integrated.minimumContrastRatio` is 1, because Visual Studio Code otherwise shifts text below 4.5:1 contrast, which turned `#ed225d` on `#f0f0f0` (about 3.7:1) dark red. A theme cannot change this setting. Source: https://code.visualstudio.com/docs/terminal/appearance
- The setup script installs the MesloLGS NF font by downloading it from Powerlevel10k's media repository, not by bundling it, because redistribution terms are unconfirmed. Shipping a finished prompt config skips the `p10k configure` wizard that would otherwise offer the font. Source: https://github.com/romkatv/powerlevel10k/blob/master/font.md
- iTerm2 loads profiles live from `~/Library/Application Support/iTerm2/DynamicProfiles/`. This could set font and colors without menus, but it is not built, and it is unconfirmed whether a dynamic profile can become the default without a click.
- The blue right-pointing triangle beside the prompt is an iTerm2 mark indicator. It is hidden only through Preferences > Profiles > Terminal > "Show mark indicators", not through the prompt config.
- The `.zshrc` color block does nothing in the built-in macOS Terminal.
